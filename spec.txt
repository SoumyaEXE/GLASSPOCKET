00 / How to use this document

Operating instructions for the implementing agent. Read this section fully before writing any code.

This document is the single source of truth for the GLASSPOCKET build. It is written to be executed by an autonomous
coding agent with a human operator reviewing at checkpoints. Every section is normative. Where a value is specified, use
that value exactly rather than substituting a preference.

Execution rules

 1. Build in the order given in Section 09. The order is dependency-sorted and risk-sorted. The riskiest item, the
    differential privacy policy, is deliberately first because it is the only component that can fail in a way that cannot be
    fixed later.

 2. Do not begin the Streamlit application until the data layer passes its acceptance checks. A beautiful frontend
    over an empty warehouse is worth zero points in this challenge.

 3. Never call an external network service from inside Snowflake. The account is a trial account. External network
    access is unavailable and will fail at compile time with error 509009. All outbound work happens in the Node bridge
    described in Section 08.

 4. Precompute aggressively. Nothing heavier than a single indexed SELECT may execute during the demo. Every
    embedding, similarity pair, geospatial join and blockchain asset ID is materialised into a table before demo time.

 5. Label synthetic data everywhere it appears. This is a project about fraud. Presenting fabricated evidence as real
    would be self-defeating and dishonest. Section 05 defines the labelling contract.

 6. Commit continuously with meaningful messages. The challenge requires that the repository be created and
    completed inside the contest window. A commit history that shows the weekend of work is itself evidence of
    compliance.

NAMING

The project is GLASSPOCKET, one word, all caps in headings, lowercase glasspocket in code identifiers, database
name GLASSPOCKET . The name refers to the "glass pockets" principle in philanthropy, the idea that an
organisation handling public generosity should be transparent enough that anyone can see into its pockets.

01 / Mission and judging context

What is being built, why, and against which scoring rubric.

The problem, in one paragraph

The most common charitable fraud is not an invented organisation. It is a real organisation with the serial numbers filed
off: a near-identical name, a copied mission statement, a cloned campaign page with one extra character in the URL.
String matching cannot catch this because the strings are deliberately different. Meanwhile, on the disbursement side,
aid that is genuinely raised is frequently diverted before it reaches a beneficiary, and the sector's answer is a PDF annual
report published nine months later. GLASSPOCKET attacks both halves: it detects impersonation by meaning rather than
spelling, it detects diversion by geography and timing, it publishes the resulting statistics under a mathematical privacy
guarantee so that beneficiaries cannot be re-identified, and it writes a public, tamper-evident receipt for every verified
disbursement so a donor can check the claim without trusting anybody.

02 / Hard constraints and known traps

Verified platform limits. Each of these has cost a builder hours. Read before provisioning.

     TRAP 01 / UNRECOVERABLE

    Select Enterprise Edition at Snowflake signup. Differential privacy requires Enterprise Edition or higher. Cloud
    platform, region and edition are chosen during signup and cannot be changed afterwards. Choosing Standard
    means the centrepiece feature of this build is permanently unavailable on that account and the only remedy is
    creating a new trial. Verify the edition immediately after login with SELECT CURRENT_EDITION(); before writing
    any other code.

     TRAP 02 / ARCHITECTURAL

    Trial accounts have no external network access. Any attempt to create an external access integration or call out
    from a UDF fails with error 509009. This is why the Solana bridge is an outbound-polling Node process that
    reaches into Snowflake, rather than Snowflake reaching out to an RPC. Do not attempt to invert this.

     TRAP 03 / SILENT

    Streamlit in Snowflake enforces a Content Security Policy that blocks scripts, styles, fonts and iframes from
    any external domain. A Geist font linked from a CDN will silently fall back to a system font. The font must be
    embedded as base64 inside the stylesheet, see Section 03. Third-party components that make external calls,
    including pyvis and streamlit-agraph, will not work. Use Plotly and pydeck, which are available in the Snowflake
    Anaconda channel.

     TRAP 04

    Map tiles require accepting External Offerings Terms. st.map and st.pydeck_chart draw tiles from Carto on
    current Streamlit versions, and Carto is a third-party offering. Accept the terms in Snowsight in the first ten
    minutes of the build, otherwise the geospatial tab renders empty with no obvious error.

     TRAP 05

    Differential privacy is incompatible with several things you will want to do. A privacy policy cannot coexist with
    an aggregation policy or a masking policy on the same object. A privacy-protected table blocks row-level SELECT
    entirely. A Dynamic Table that depends on a privacy-protected object will fail to refresh. Consequence: the privacy
    policy attaches only to a terminal serving view at the very end of the pipeline, never to a table in the middle of the
    DAG.

     TRAP 06

    Vector similarity at general availability performs an exact scan. A self-join across an organisation table with no
    pre-filter is a full cross product and will consume the credit budget in a single query. Every similarity query in this
    specification carries a metadata pre-filter. Do not remove it.

GLASSPOCKET / Build Specification v1.0                                                                                       5
TRAP 07

Streamlit in Snowflake has a 32 MB limit on data passed from backend to frontend in a single command.
Never render an unbounded dataframe. Every table in this specification carries an explicit LIMIT.

TRAP 08

Compressed NFT reads require a DAS-enabled RPC endpoint. The default public devnet endpoint does not
serve the Digital Asset Standard API. Use a Helius devnet endpoint. Parse asset IDs only from transactions at
finalized commitment, and poll with retries because there is an indexing delay between mint and DAS availability.
Mitigation: mint the demo receipts hours before recording, never live.

TRAP 09

The trial credit budget is finite. Set warehouse auto-suspend to 60 seconds immediately after account creation.
Use an XSMALL warehouse for everything in this build. Embeddings are generated once, in a single batch, and
never regenerated on application load. If an embedding query is written inside a Streamlit render path, that is a
defect.

03 / Design system

The application must not look like a default Streamlit app. This section is not decoration, it is a scored criterion.

Typography

The single typeface is Geist, the Vercel sans-serif. It is used for every element without exception: headings, body, labels,
numerals, table cells, chart axis labels, chart tooltips and code-like strings such as asset identifiers and SQL fragments.

     ABSOLUTE RULE / NO MONOSPACE

    No monospaced typeface appears anywhere in the application. Not Geist Mono, not Source Code Pro, not the
    browser default. Where the interface displays a Solana asset identifier, a wallet address, an EIN or a SQL snippet, it
    is set in Geist with the OpenType tabular-figures feature enabled and a tinted background block. Any element that
    resolves to a monospace font is a defect. Explicitly override Streamlit's built-in code styling; do not rely on
     st.code , which forces monospace. Build a custom rendering helper instead, see below.

Embedding Geist under the Content Security Policy
Because external font hosts are blocked, Geist must be inlined. Obtain the woff2 files from the npm package geist ,
subpath dist/fonts/geist-sans/ . Required weights: 400 Regular, 500 Medium, 600 SemiBold, 700 Bold. Base64 each
file and emit a single stylesheet at application start.

    # tools/build_font_css.py, run once, output committed to the repo
    import base64, pathlib
    WEIGHTS = {"Regular": 400, "Medium": 500, "SemiBold": 600, "Bold": 700}
    faces = []
    for name, weight in WEIGHTS.items():

       raw = pathlib.Path(f"fonts/Geist-{name}.woff2").read_bytes()
       b64 = base64.b64encode(raw).decode()
       faces.append(

          "@font-face{font-family:'Geist';font-style:normal;"
          f"font-weight:{weight};font-display:block;"
          f"src:url(data:font/woff2;base64,{b64}) format('woff2');}}"
       )
    pathlib.Path("app/assets/geist.css").write_text("".join(faces))

Inject it in the application, together with the global override, as the very first Streamlit call after page configuration:

    # app/theme.py
    import streamlit as st, pathlib

    def inject_theme():
       font_css = pathlib.Path("assets/geist.css").read_text()
       st.markdown(f"<style>{font_css}{GLOBAL_CSS}</style>", unsafe_allow_html=True)

    GLOBAL_CSS = """
    html, body, [class*="css"], [data-testid] , button, input, textarea, select,
    code, pre, kbd, samp, .stMarkdown, .stDataFrame, .js-plotly-plot, .plotly {

      font-family: 'Geist', -apple-system, sans-serif !important;
      font-feature-settings: 'tnum' 1, 'cv01' 1;
    }

Layout primitives

  · Spacing scale. 4, 8, 12, 16, 24, 32, 48, 64 px. No arbitrary values.
  · Radius. 6 px on cards, 4 px on chips and inputs, 999 px on pills. Charts have no radius.
  · Elevation. None. Separation comes from a single 1 px border in the border token. No drop shadows anywhere.
  · Grid. Twelve columns implemented with st.columns . Maximum content width 1180 px.
  · Hero pattern. Every tab opens with one oversized figure in the display token, one line of context beneath it in the

    label token, and nothing else above the fold. This is what converts a dashboard into a narrative.

Chart styling contract

Every Plotly figure passes through a single helper so that styling cannot drift. Implement it once in app/charts.py and
route all figures through it.

    def style_fig(fig, height=340, legend=False):
       fig.update_layout(
          font=dict(family="Geist", size=13, color="#16181D"),
          paper_bgcolor="rgba(0,0,0,0)", plot_bgcolor="rgba(0,0,0,0)",
          margin=dict(l=8, r=8, t=28, b=8), height=height,
          showlegend=legend, hoverlabel=dict(font_family="Geist", font_size=13),
          xaxis=dict(showgrid=False, zeroline=False, linecolor="#E4E7EB"),
          yaxis=dict(gridcolor="#F0F2F4", zeroline=False, linecolor="#E4E7EB"),
       )
       return fig

CHART RULES

No chart titles inside the figure; the title is a Streamlit heading above it, so typography stays consistent. No
gridlines on the x axis. No legend unless two or more series genuinely overlap. Colour carries meaning strictly
according to the palette table, so a red bar always means flagged and an amber line always means privacy noise.
Animation is used exactly twice in the whole application, both specified in Section 07.

The synthetic adversary set, and the labelling contract

There is no public labelled dataset of fake charities, because fakes are taken down rather than catalogued. Therefore the

Generation rules
 tools/make_synthetic.py produces roughly 400 adversarial organisations by sampling real BMF entries and applying
transformations that mirror documented real-world techniques:

  · Semantic clone. Replace one word with a synonym while preserving meaning, for example Relief becomes Aid,
    Foundation becomes Trust, Children becomes Kids.

  · Token reorder. Same words, different order, plus a filler word such as National or United.
  · Homoglyph and spacing. A doubled letter, a hyphen inserted, an abbreviation expanded.
  · Disaster attachment. Append a current disaster keyword to a legitimate base name, mirroring the documented post-

    wildfire domain pattern.
  · Geographic implausibility. Assign disbursement coordinates far outside any plausible operating radius for the

    organisation's registered address.

-- sql/07_clone_detection.sql

CREATE OR REPLACE TABLE MARTS.CLONE_PAIRS AS

SELECT

s.org_id AS suspect_id, s.name AS suspect_name,

t.org_id AS target_id, t.name AS target_name,

s.city, s.state, s.cause,

VECTOR_COSINE_SIMILARITY(s.name_vec, t.name_vec) AS semantic_sim,

JAROWINKLER_SIMILARITY(s.name, t.name) / 100.0 AS string_sim,

-- the gap between meaning and spelling is the whole thesis

VECTOR_COSINE_SIMILARITY(s.name_vec, t.name_vec)

- (JAROWINKLER_SIMILARITY(s.name, t.name) / 100.0) AS evasion_gap

FROM STAGING.ORGS s

JOIN STAGING.ORGS t

ON s.region_h3 = t.region_h3 -- REQUIRED pre-filter, see Trap 06

AND s.cause = t.cause

AND s.ein <> t.ein

WHERE s.is_synthetic = TRUE             -- suspect side is ALWAYS seeded

AND t.is_verified = TRUE                -- target side is ALWAYS a real, good-standing org

QUALIFY VECTOR_COSINE_SIMILARITY(s.name_vec, t.name_vec) >= 0.86;

Why evasion_gap matters. A high semantic similarity paired with a low string similarity is the signature of deliberate
evasion: the impersonator kept the meaning and changed the spelling on purpose. This single derived column is the
most quotable number in the entire project and it drives the primary chart on the Donor tab.

06.5 The risk score, decomposable by design

An opaque score is unusable in an accountability tool. The score must be reconstructable by hand from its components,
and the interface must show the components. Implement as a SQL UDF so it is inspectable.

    CREATE OR REPLACE FUNCTION MARTS.F_RISK(
       semantic_sim FLOAT, evasion_gap FLOAT,
       geom_flags INT, unaccounted_ratio FLOAT, missing_receipts INT)

    RETURNS FLOAT
    AS $$

      LEAST(100,
         35 * GREATEST(0, (semantic_sim - 0.86) / 0.14)

       + 25 * LEAST(1, evasion_gap / 0.45)
       + 20 * LEAST(1, geom_flags / 5.0)
       + 12 * LEAST(1, unaccounted_ratio)
       + 8 * LEAST(1, missing_receipts / 10.0))
    $$;

Why a public ledger belongs here

State this argument explicitly in the write-up, because the weakest submissions in any blockchain category are the ones
that cannot answer it. A donor verifying a claim about a charity is verifying it against a record kept by the charity, or by a
platform the charity pays, or by an application built by someone they have never met. Every one of those requires trust in
an interested party. A compressed NFT receipt is a record that persists whether or not GLASSPOCKET exists, whether or
not the operator stays honest, and whether or not the warehouse is later edited. That property is the only reason a chain
is here, and it is a real property rather than a decorative one.

What goes on chain, and what must not

The receipt metadata carries a claim, never a person. Fields: programme code, amount band rather than exact amount,
delivery window rather than exact timestamp, a salted hash of the organisation identifier, and a schema version. No
beneficiary identifier, no coordinates, no name, no exact figure. The rule to state in the post is: publish the claim, not the

const umi = createUmi(HELIUS_DEVNET_RPC).use(mplBubblegum());
umi.use(keypairIdentity(loadKeypairFromEnv()));

while (running) {

   const batch = await claimBatch(50);           // UPDATE ... SET status='CLAIMED' RETURNING

   for (const row of batch) {

      try {

         const sig = await mintToCollectionV1(umi, {

         leafOwner: TREASURY, merkleTree: TREE, collectionMint: COLLECTION,

         metadata: buildReceiptMetadata(row),

         }).sendAndConfirm(umi, { confirm: { commitment: "finalized" } });

         const assetId = await parseLeafFromMintToCollectionV1Transaction(umi, sig.signature);

         await writeMintLog(row, assetId, sig);

      } catch (e) {

         await markFailed(row, e);      // never crash the loop

      }

   }

   await sleep(4000);

}
